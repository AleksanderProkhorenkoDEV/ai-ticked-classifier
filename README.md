# AI Ticket Classifier

A small incident-management app that uses an LLM to do the boring part of triage. You write a
title and a description; the model reads it and assigns a **category**, a **urgency** and a
**sentiment** on its own. Nothing else to fill in.

The project exists to learn how to wire an LLM API to a real database with real data — the
classification is the excuse, the Spring AI + JPA + Testcontainers plumbing is the point.

---

## Features

- **Automatic classification** — `POST /tickets/create` sends title + description to
  `ministral-3b-2512` and stores the returned category, urgency and sentiment on the ticket.
- **Dashboard** with a paginated table of tickets.
- **Filters** by urgency, by category and by free-text search over the title.
- **Inline status change** — a `<select>` in each row calls `PATCH /tickets/update-status/{id}`
  and optimistically updates the row; it reverts if the call fails.
- **Four KPI cards** — Total, Open, High urgency, Resolved. They refresh themselves when a
  ticket is created or archived.
- **Responsive sidebar** that collapses under 1024px and closes on `Escape` or on navigation.
- **Toast notifications** wired through custom DOM events, so components stay decoupled.

## Architecture

```
Browser (Lit + Open Cells)
        │  fetch ${VITE_API_URL}/tickets…
        ▼
TicketController            ← @RequestMapping("/tickets")
        │
        ▼
TicketServices              ← validation-free domain logic, transaction boundary
        ├──► TicketRepository          ──►  MySQL
        └──► TicketClasificationServices
                     │
                     │  ChatModel.call(prompt, jsonSchema)
                     ▼
               Mistral API  ──►  {"category":"BUG","feeling":"NEGATIVO","urgency":"ALTA"}
```

The classifier returns a `TicketClasification` record, which the service turns into a
`Ticket` and saves. Every ticket is created with status `ABIERTO` and `archived = false`.

### Backend layout

```
backend/ticked-classifier/src/main/java/dev/aprokhorenko/ticked_classifier/
├── configuration/   Webconfig (CORS)
├── controllers/     TicketController, GlobalExceptionController
├── dto/             Request / response records and Lombok DTOs
├── entities/        Ticket + the four enums
├── mappers/         TicketMapper (entity → DTO)
├── repositories/    TicketRepository (JpaRepository + one JPQL query)
└── services/        TicketServices, TicketClasificationServices
```

### Frontend layout

```
frontend/src/
├── components/      Lit custom elements (navigation, dashboard, form, toast)

├── css/             styles exported as CSSResultGroup literals
├── lib/action/      fetch wrappers, one per endpoint
├── pages/           home-page, dashboard-page, create-ticket-page
```

## Getting started

### 1. Environment variables

The root `.env` is gitignored. Create it from the example and fill it in:

```sh
cp .env-example .env
```

| Variable | Used by | Example |
|---|---|---|
| `MYSQL_PORT` | `spring.datasource.url`, docker-compose port mapping | `3307` |
| `MYSQL_DATABASE` | `spring.datasource.url` | `tickets` |
| `MYSQL_ROOT_PASSWORD` | `spring.datasource.password` | *(secret)* |
| `MISTRAL_URL` | `spring.ai.mistralai.base-url` | `https://api.mistral.ai` |
| `MISTRAL_API_KEY` | `spring.ai.mistralai.api-key` | *(secret)* |

All five are required — `application.properties` references each one as a placeholder, so a
missing value fails at startup with `Failed to parse placeholder`.

### 2. Start MySQL

```sh
make up      # docker compose up -d
make logs    # tail the logs
make down    # stop it
```

`make clean` also deletes the volume. Only run it if you want to throw the data away.

### 3. Run the backend

Spring does **not** read `.env`, so export the variables first:

```sh
set -a && . ./.env && set +a
cd backend/ticked-classifier
./mvnw spring-boot:run
```

The API comes up on port 8080. Alternative: the VS Code launch configurations in `.vscode/`,
which read `envFile` for you.

### 4. Run the frontend

```sh
cd frontend
pnpm install
pnpm dev        # http://localhost:5173
```

`frontend/.env` only needs the backend URL:

```sh
VITE_API_URL=http://localhost:8080
```

### 5. Check the whole flow

Create a ticket from the UI (or `curl`, below), then open the dashboard: the new row should
appear with the category, urgency and sentiment the model chose.

## API reference

Base URL `http://localhost:8080`. CORS is restricted to `app.cors.allowed-origins`
(`http://localhost:5173` plus the deployed origin) and to methods `GET`, `POST` and `PATCH`.

### `GET /tickets`

Paginated list with optional filters.

| Param | Type | Default | Notes |
|---|---|---|---|
| `page` | int | `0` | zero-based |
| `size` | int | `10` | |
| `urgency` | enum | — | `BAJA`, `MEDIA`, `ALTA` |
| `category` | enum | — | `BUG`, `CONSULTA`, `INCIDENCIA` |
| `search` | string | — | case-insensitive `LIKE` over the title |

```sh
curl "http://localhost:8080/tickets?page=0&size=10&urgency=ALTA&search=imagen"
```

```json
{
  "content": [
    {
      "id": 1,
      "title": "Error al subir imagenes",
      "description": "Al subir una imagen sale un error 500 en la pantalla de perfil.",
      "date": "2026-01-15T10:30:00",
      "category": "BUG",
      "urgency": "ALTA",
      "feeling": "NEGATIVO",
      "status": "ABIERTO"
    }
  ],
  "currentPage": 0,
  "totalPages": 1,
  "totalElements": 1
}
```

### `POST /tickets/create`

```sh
curl -X POST http://localhost:8080/tickets/create \
  -H 'Content-Type: application/json' \
  -d '{"title":"Error al subir imagenes","description":"Sale un error 500 al subir una imagen."}'
```

```json
{ "message": "Ticked creado", "status": 201 }
```

Both fields are `@NotEmpty`; a missing one returns `400` with the field name and the message
from `ValidationMessages.properties`.

### `PATCH /tickets/update-status/{id}`

```sh
curl -X PATCH http://localhost:8080/tickets/update-status/1 \
  -H 'Content-Type: application/json' \
  -d '{"status":"EN_PROGRESO"}'
```

`status` accepts `ABIERTO`, `EN_PROGRESO`, `CERRADO`, `ARCHIVADO`. An unknown id returns `404`.

### `GET /tickets/stats`

```json
{ "total": 42, "open": 17, "high": 8, "resolved": 11 }
```

## The AI layer

`TicketClasificationServices` builds a Spanish prompt from the title and description, asks
Mistral for a JSON-schema-constrained answer, and deserialises it:

```java
var options = MistralAiChatOptions.builder()
        .model(MistralAiApi.ChatModel.MINISTRAL_3B.getValue())
        .responseFormat(ResponseFormat.jsonSchema(TicketClasification.class))
        .build();
```

The schema is derived from the record itself, so the model is constrained to
`category` / `feeling` / `urgency` with the exact enum values the database uses.

An LLM has three outcomes in production and all three are handled explicitly:

| Situation | Result |
|---|---|
| Valid JSON | ticket saved |
| Call fails (network, auth, rate limit) | `RuntimeException("No se pudo obtener respuesta del LLM")` |
| Answer is not the expected shape | `RuntimeException("El modelo tiene un formato inesperado")` |

Because the classifier runs inside `createTicked`'s transaction, a failed classification means
nothing is written to the database.

## Data model

Table `tickets`, generated by JPA:

| Column | Type | Notes |
|---|---|---|
| `id` | bigint | identity |
| `title` | varchar | not null |
| `description` | varchar | not null |
| `date` | datetime | not null, not updatable, set on construction |
| `category` | enum as string | `BUG`, `CONSULTA`, `INCIDENCIA` |
| `urgency` | enum as string | `BAJA`, `MEDIA`, `ALTA` |
| `feeling` | enum as string | `NEGATIVO`, `NEUTRO`, `POSITIVO` |
| `status` | enum as string | `ABIERTO`, `EN_PROGRESO`, `CERRADO`, `ARCHIVADO` |
| `archived` | boolean | derived from `status == ARCHIVADO`, not set directly |

## Testing

41 tests across 5 classes. Each one uses a deliberately different technique, because mocking
everything would leave the interesting parts untested.

| Test class | Technique | Why |
|---|---|---|
| `TicketControllerTest` | `@WebMvcTest` + `@MockitoBean` | Loads only the web layer: no DB, no LLM. Service is mocked, but `TicketMapper` is imported for real so the mapping is exercised. |
| `TicketServicesTest` | plain Mockito, no Spring | Service is built by hand, so the tests run in milliseconds. Verifies the classifier's result is persisted and that nothing is saved when it fails. |
| `TicketClasificationServicesTest` | plain Mockito on `ChatModel` | An interface mock gives a fake in-memory model: no network, no key, no bill, always the same answer. Covers all three LLM outcomes. |
| `TicketRepositoryTest` | `@DataJpaTest` + Testcontainers (real MySQL) | `findFiltered` is JPQL with `LOWER` / `LIKE` / `ORDER BY` — exactly the thing a mocked repository cannot verify. |
| `TickedClassifierApplicationTests` | `@SpringBootTest` + Testcontainers | Smoke test: the full context starts. |

```sh
set -a && . ./.env && set +a       # the @SpringBootTest context resolves the placeholders
cd backend/ticked-classifier
./mvnw test
```

Docker must be running (Testcontainers pulls `mysql:latest`). To iterate on a single class:

```sh
./mvnw test -Dtest=TicketControllerTest
```

`TestTickedClassifierApplication` is a `main()` in the test sources that boots the whole app
against Testcontainers — useful for exercising the LLM + DB flow without `make up`.

### Frontend

There is no test runner. `pnpm build` is the only automated check: it runs `tsc` first, so it
typechecks, then builds with Vite. `tsconfig.json` has `noUnusedLocals` and
`noUnusedParameters` on, and `emitDeclarationOnly`, so `.d.ts` files land in `./types/`
(gitignored).

## Non-obvious decisions

Things that look wrong or redundant until you know why.

- **The API path is `/tickets`, not `/tickeds`.** The project directory and many identifiers
  use the "ticked" spelling, but the mapping is the English one. `AGENTS.md` documented the
  wrong path for a while; the code is the source of truth.
- **`TicketControllerTest` lives in `org.springframework.boot.webmvc.test.autoconfigure`.**
  The package moved in Spring Boot 4 — the old `@WebMvcTest` package no longer exists.
- **`@MockitoBean`, not `@MockBean`.** `@MockBean` was removed in Spring Boot 4.
- **`TicketMapper` is imported explicitly in the web slice test.** It is a `@Component`, so
  `@WebMvcTest` does not pick it up; importing it means the real entity → DTO mapping runs
  instead of a mock that would return nulls.
- **Stubs are set per test, not in `@BeforeEach`, in the Mockito tests.** `MockitoExtension`
  runs in strict mode and fails a test that declares a stub it never uses.
- **`TestTickedClassifierApplication` is not a test.** It is a `main()` under
  `src/test/java` that boots the app with `SpringApplication.from(...).with(TestcontainersConfiguration.class)`.
- **Every component must be imported from `src/components/index.ts`.** Custom elements only
  register when the module is imported; `index.html` loads the barrel, so a new element that is
  not added there silently never renders.
- **CORS is restricted to three methods.** `DELETE` is not in the allow list.
- **`.env-example` used to be missing `MISTRAL_URL`,** which broke startup if you followed it
  literally. It now lists all five variables.

## Conventions

- **Languages:** code, identifiers, comments and commit messages are in English. Everything the
  user sees — UI labels, button text, toasts, API error messages — is in Spanish. Tests follow
  the same split: `@DisplayName` values are Spanish, identifiers are not.
- **Branches** are named `<issue#>-<slug>`, e.g. `21-unit-test`.
- **Commits** follow [conventional commits](https://www.conventionalcommits.org/): `feat:`,
  `fix:`, `refactor:`, `style:`, `test:`, `docs:`.
- **Everything lands on `main` through a PR.** Never push directly to `main`.
- `AGENTS.md` holds the agent-facing handbook (commands, boundaries, verification). This file
  is the human-facing onboarding.

## Known quirks

Things that are true today but look like mistakes. None of them are fixed yet:

1. **`POST /tickets/create` answers HTTP 200 with `status: 201` in the body.** The controller
   wraps a `GlobalResponseDTO` in `ResponseEntity.ok(...)` while putting
   `HttpStatus.CREATED.value()` inside the payload. Clients checking `response.ok` are fine;
   clients asserting on `status === 201` at the HTTP level are not.
2. **The "Resolved" KPI counts archived tickets, not closed ones.** `getTicketStats()` fills
   the `resolved` field with `countByArchivedTrue()`, and `archived` is derived from
   `status == ARCHIVADO`. So `CERRADO` tickets are not counted as resolved anywhere.
3. **`frontend/src/lib/action/create.ts` declares a `TicketResponseDTO` with Spanish field
   names** (`titulo`, `categoria`, …) that do not match the actual API response. The shape is
   unused by the caller, so it does not break today, but it is misleading.
4. **No CI.** There is no workflow, no linter and no formatter configured for either project.
